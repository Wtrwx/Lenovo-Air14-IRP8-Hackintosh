## 2. 标准 H.264 硬件编码修复（`tools/patch_tgl_vadriver_h264.py`）

- **问题现象**：此前在 `0.4.4` 与 `VA1`（已拦截低延迟 `feature=0x400` 防 VCS0 挂起）下，标准 H.264 硬件编码（`feature=0x4000`）出现严重码率膨胀（`1.4 Mb/s` 目标实测输出 `12.23 Mb/s`、静止帧达 `4.08 Mb/s`）、画面竖条纹、运动边缘残影与高噪点。
- **定位到的根因**：`AppleIntelTGLGraphicsVADriver` 内 `MhwStateHeapInterface::SetSurfaceState` 的 `MEDIA_SURFACE_STATE.DW2` 路径（文件偏移 `0x5f048`）在 `bUsesPatchList == 1` 提交 KMD `SurfacePitch` patch 前未清零 `DW2` 预写入的 `(dwPitch - 1) << 3`，导致 KMD 再次叠加 `(kmd_pitch - 1) << 3`（双倍 pitch）。这使 `CodechalEncodeAvcEncG12` 的 VME/MbEnc 读取错位参考帧步幅，而 `PAK`（其 `MFX_SURFACE_STATE` 已由 `TGLVA` 在 `0x1a1a20` 清零）按原画面硬编出巨大残差与错乱模式决策。
- **手术级修补**：使用 [tools/patch_tgl_vadriver_h264.py](../tools/patch_tgl_vadriver_h264.py)（`--mode hw-encode-fix`）在保留 `VA1` 全套 `feature=0x400` 拦截与 34-root ABI 修正的基础上，仅将 `0x5f048` 的 `c1 e0 03` 改为 `31 c0 90`（`xorl %eax, %eax; nop`），与 `TGLVA` 对 `MFX_SURFACE_STATE` 的清零方式完全对称，不修改 `TGLVA` 代码段。同时保留 `--mode sw-fallback` 作为纯软件编码回退方案。
- **真机实测对比（`verify_vt_h264.mm` + `run_verify_vt_h264.py`，macOS `25G332` 实跑）**：

| --- | --- | --- | --- | --- | --- | --- |
| `default-rate` | 标准硬编 | `1728×1080` / 24f | 无限制 | `37.72 Mb/s` / `47.56 dB` | **`2.021 Mb/s` / `57.82 dB`** | `2.56 KB` |

## 3. 蓝牙稳定性修复：`IntelBTUnified 1.0.1` + AX211 `2026-01-28` 固件注入

- **根因**：此前 `BlueToolFixup 2.7.2` 内存修补 `/usr/sbin/bluetoothd` 4 个代码页在 Tahoe APFS 压缩页重读时持续触发代码签名页失配与 `SIGBUS` 循环崩溃；而原生 `IntelBTUnified 1.0.1` 虽通过 `_vnode_pagein` 消除了页签名 `SIGBUS`，但其自带的 AX211（`8087:0033`）`2023-10-17` 固件缺少 `HCI_LE_Read_Buffer_Size [v2]` 能力掩码（byte 41 为 `0xC8`），导致 macOS `26.7.2` 上 `bluetoothd` 报 `OI_HCICMD_LE_Read_BufferSize_V2 (status=628)` 后退出重启。
- **方案与工具**：使用 [tools/patch_intelbtunified_ax211_fw.py](../tools/patch_intelbtunified_ax211_fw.py) 从正常工作的 `IntelBluetoothFirmware 2.5.3` 提取 `2026-01-28` / `2024-01-31` AX211 固件（`ibt-0040-0041.{ddc,sfi}`、`ibt-0040-1020.sfi`、`ibt-0041-0041.sfi`、`ibt-1040-{0041,1020}.sfi`），直接写入 `IntelBTUnified` 对应 `__TEXT,__const` 槽位并更新 `_fwList`（校验 85/85 条 zlib 一致性，不改动加载命令、符号表或 `_vnode_pagein`）。
- **实机验证**：已替代 `IntelBluetoothFirmware` + `IntelBTPatcher` + `BlueToolFixup` 在本机部署并重启验证，`local.IntelBTUnified (1.0.1)` 加载正常，固件版本 `v12490 c12490`，`bluetoothd` `runs=1`、无崩溃退出，蓝牙键盘连接正常（音频并发与多次长睡眠待续测）。

## 4. 外屏 HiDPI 碰撞与系统设置“显示器”空白卡死修复

- **根因 1（系统设置卡死/空白与切换延迟）**：外屏 Display Override 被写入 242 项 `scale-resolutions`，在 `WindowServer` 展开为 `1,952` 个 CGS 模式；`MonitorPanel.framework` 为每个模式发出 3 次同步 SkyLight Mach IPC，实测 `+[MPDisplayMgr sharedMgr]` 阻塞 `15.36–40.55 s`（$O(N^2)$ 复杂度），造成“显示器”面板空白与侧栏切换延迟。
- **根因 2（`1920×1080 HiDPI` 消失）**：当 `scale-resolutions` 中在 16 字节 HiDPI 条目之前同时存在同分辨率（如 `3840×2160`）的 8 字节 LoDPI 条目时，`IOFramebuffer` 优先将其注册为普通模式而不带 `0x00200000` 标志，导致 `WindowServer` 拒绝切换 `1920×1080 HiDPI`。
- **修复与工具更新**：
  - 将外屏 `Q24T09`（`0x4d67:0x2409`）精简为 15 项零碰撞标准 16:9 条目（`6` 项 LoDPI `≤ 2048×1152` + `9` 项 HiDPI `2560×1440..5120×2880`），实测 `MPDisplayMgr sharedMgr` 耗时由 `35.9 s` 降至 **`0.545 s`**，系统设置秒开且 `3840×2160 / UI 1920×1080 @ 144Hz` 与内屏 `2880×1800 / UI 1440×900 @ 120Hz` 同屏正常工作。
  - 更新 [tools/make_hidpi_override.py](../tools/make_hidpi_override.py)：默认仅输出 16 字节 `0x200000` HiDPI 条目，新增可选 `--lodpi` 参数并在检测到同背板分辨率碰撞时直接报错拒绝生成，条目总数超过 32 项时给出卡死预警。

## 5. 系统级稳定性运维经验：`logd` 写盘压力与 FAT32 ESP 维护

- **`logd` 120s watchdog 超时定位**：实机曾记录 `WindowServer` 在高刷外屏合成期间通过 `com.apple.SkyLight`（`tracing.stalls` / `performance_instrumentation`）高频写盘 `Signpost`（约每 `70–94 s` 轮转 `13 MB`）叠加残留内核过滤，引发 `logd` 队列超时 panic。通过系统自带接口关闭这两项持久化 signpost 与重置内核过滤可显著降低日志写盘压力：
  ```sh
  sudo log config --process kernel --reset
  sudo log config --subsystem com.apple.SkyLight --category tracing.stalls --mode signpost-persisted:off
  sudo log config --subsystem com.apple.SkyLight --category performance_instrumentation --mode signpost-persisted:off
  ```
- **ESP FAT32 写入规范**：在 macOS 下更新 `EFI/OC` 时务必使用 `COPYFILE_DISABLE=1`（并清理 `._*` AppleDouble 文件），每次维护前后使用 `fsck_msdos -n /dev/rdiskXs1` 核查分区健康，避免 FAT32 目录项损坏导致 OpenCore 启动报 `Info.plist is missing for injected kext`。
